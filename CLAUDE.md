# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

h2s is an intranet link dashboard: ASP.NET Core Razor Pages on .NET 10, EF Core + SQLite, Bootstrap 5.3. The app is `h2s/`; `h2s.Widgets.Abstractions/` is the class library integrations are written against (see Integrations below).

## Commands

Run from the repository root:

- Build: `dotnet build h2s/h2s.csproj`
- Create the dev database with sample data: `./scripts/new-dev-db.ps1` or `scripts/new-dev-db.sh`. Add `-Reset` / `--reset` to replace an existing one, and `-From <path>` / `--from <path>` to snapshot an existing database (e.g. a prod copy) instead of seeding. Both wrap `dotnet run --project h2s/h2s.csproj -- seed [--reset] [--from <path>]`, which is Development-only.
- Run (http://localhost:5284, Development): `dotnet run --project h2s/h2s.csproj`
- Add migration: `dotnet ef migrations add <Name> --project h2s/h2s.csproj --startup-project h2s/h2s.csproj --output-dir Migrations`
- Apply migrations manually: `dotnet ef database update --project h2s/h2s.csproj --startup-project h2s/h2s.csproj` (normally unnecessary: `Program.cs` calls `Database.Migrate()` on startup)
- Container: `docker build -t h2s:local -f h2s/Dockerfile .` (or `wslc build` on Windows). The build context is the repo root, so `Directory.Build.props` and `.editorconfig` apply; the root `.dockerignore` limits what is sent.
  - The build stage publishes for `$TARGETARCH`, so only that architecture's native SQLite library ships.
  - The Dockerfile copies `h2s/` and `h2s.Widgets.Abstractions/`; a new project the app references needs its own `COPY` line and an entry in `.dockerignore`.
  - The image runs as `$APP_UID` (1654). Deployments may override the UID to match the data volume, so nothing outside `/app/data` may need to be writable.
  - `Microsoft.EntityFrameworkCore.Tools` is `Publish="false"`: `dotnet ef` needs it in the build output, but its Roslyn and MSBuild dependencies stay out of the image. Don't add design-time packages without the same treatment.

- Test: `dotnet test --solution h2s.slnx`. For a single test, add `--filter-method "*Post_SavesValidSettings"`; `--filter-class` and `--filter-namespace` also work.

Tests are xUnit v3 in `tests/h2s.Tests`, run on Microsoft.Testing.Platform. `global.json` opts `dotnet test` into MTP, which the .NET 10 SDK requires for xUnit v3, so `dotnet test` takes `--solution`/`--project` rather than a positional path.

- `Unit/` tests use `TestDatabase`, a migrated in-memory SQLite database, optionally seeded.
- `Integration/` tests host the app with `DashboardApplicationFactory` over a private in-memory database seeded by `DevDataSeeder`, with Data Protection keys held in memory. Create one factory per test that changes data.
- Posting to Razor handlers needs an antiforgery token; use `FormPoster.PostAsync`.
- Pass `TestContext.Current.CancellationToken` to async calls; the xUnit analyzers flag it otherwise.

Code style:
- Restore the pinned tools (`jb`, `dotnet-ef`) with `dotnet tool restore`; they're listed in `dotnet-tools.json`.
- Format exactly as CI does with `dotnet jb cleanupcode h2s.slnx --include="**/*.cs" --exclude="**/Migrations/**" --disable-settings-layers="GlobalAll;GlobalPerProduct;SolutionPersonal;ProjectPersonal"` (Built-in: Full Cleanup).
  - Narrow `--include` to a file to limit it.
  - It takes about 5 minutes because it loads the whole solution.
  - Disabling the machine-global layers keeps results reproducible. Repo settings already override them, so the IDE agrees anyway.
- `dotnet jb inspectcode h2s.slnx --output=<file> --format=Sarif` runs the ReSharper inspections.
- Don't run `dotnet format whitespace`; it fights the ReSharper alignment rules.
- The build reports the `.editorconfig` rules as warnings (`EnforceCodeStyleInBuild`). `-p:ContinuousIntegrationBuild=true` makes all warnings errors.

The connection string key is `ConnectionStrings:h2s`. Development uses `App_Data/h2s.db`. `Program.cs` resolves a relative `Data Source` against the content root (`SqliteConnectionStrings`), giving `h2s/App_Data/h2s.db`, which is gitignored and dockerignored. Production uses `/app/data/h2s.db`, a mounted volume. Don't name a data directory `data`: on Windows it collides with the `h2s/Data/` source folder. Data Protection keys persist to a `keys` directory beside the database (`SqliteConnectionStrings.GetDataDirectory`), so antiforgery tokens survive restarts. Sample data lives in `h2s/Data/Seeding/DevDataSeeder.cs`; keep it in step with schema changes, since the AddDashboardSettings migration inserts the settings row and the seeder updates it. The AddPanels migration likewise inserts the default panels, which the seeder leaves alone. Any new environment keeps the same connection string key and the SQLite provider. The app is single-instance only: SQLite with no concurrency support.

## Architecture

- **Data**: one `DashboardContext` (`h2s/Data/`) with `Categories`, `Links`, `Widgets`, `Panels`, `SearchEngines`, `Connections` and `DashboardSettings`.
  - `DashboardSettings` is a singleton row enforced by a check constraint (`Id = 1`). Always read and write it through `DashboardSettingsService`. If the row is missing, the service creates it with the defaults `Title = "Dashboard"`, empty `Motto` and `LocalDomains`, and `ColorMode = Auto`. Nothing integration-specific belongs in it: integrations keep their settings in connections.
  - The service caches the settings in `IMemoryCache` (5-minute expiry) and hands out copies, which callers may change and pass to `SaveSettingsAsync`. Saving invalidates the cache. Writes that bypass the service (the seeder, `ExecuteUpdate` in tests) show up only after expiry, so in integration tests change settings before the first request.
  - Categories and links are accessed directly through `DashboardContext` in the PageModels, with no repository layer. Don't add a service for them without a clear need.
- **Schema changes**: update the model, `DashboardContext` and a new migration together. Migrations are applied automatically at startup, including in production.
- **Pages**:
  - `Pages/Index` is the public dashboard.
    - Categories sort by `IsAdminCategory`, then `SortOrder` (then `Name`); admin categories render after a grid break, tinted red. `SortOrder` counts within a section, so regular and admin categories are ordered separately.
    - **Collapsible categories** (outside edit mode): the category's `<h2>` holds a `category-collapse-button` (name, a link count shown when collapsed, and a chevron). `category-collapse.js` toggles `is-collapsed` and `aria-expanded`, and saves the collapsed IDs, dot-separated (commas aren't safe in cookies), in the `h2s-collapsed` cookie. `ViewerPreferences.ReadCollapsedCategories` reads it into `IndexModel.CollapsedCategoryIds`, so the server renders them collapsed. Edit mode keeps the plain `<h2>` (edit-mode.js reads the name from it) and ignores the cookie. Quick launch adds `quick-launch-expanded` to a collapsed category with matches, which shows its body.
    - Links within a category sort by `SortOrder` (then `Label`). New links, and links or categories moved to another category or section, go to the end.
    - **Edit mode** (`/?edit=true`, granted only when the `Admin` policy passes; the navbar's Edit/Done button toggles it) adds drag handles. `wwwroot/js/modules/edit-mode.js` uses the vendored SortableJS to reorder categories within their section and links within or across categories, and arrow keys on a focused handle do the same. Each move posts the full ordered ID list to `OnPostReorderCategoriesAsync` / `OnPostReorderLinksAsync` on the Editor page, which renumber `SortOrder` from 0; on failure the page puts things back and shows a toast.
    - Edit mode also adds, edits and deletes links and categories through the shared `_LinkDialog` (`link-dialog.js`) and `_CategoryDialog` (`category-dialog.js`) partials, calling the Editor page's handlers. Tiles render as `_EditableLinkSlot`, and after a save the page swaps in a fresh one from `OnGetLinkSlotAsync`. The dialog's live preview is `_LinkTile` itself, rendered by `OnGetTilePreviewAsync`, so it can't drift from the dashboard. Adding a category, or moving one between sections, reloads the page.
    - Deletes return a snapshot (`LinkSnapshot` / `CategorySnapshot` in `Pages/Admin/`). The toast's Undo posts it unchanged to `OnPostRestoreLinkAsync` / `OnPostRestoreCategoryAsync`, which recreate the item (with new IDs) at its old position.
    - Each link shows a selfh.st icon when `IconName` is set, otherwise a fallback dot. Links whose host isn't in `LocalDomains` get an "External" badge. A link with `OpenInNewTab` (the link dialog's switch, off by default) renders with `target="_blank" rel="noopener noreferrer"`, and quick launch's Enter follows it because it clicks the tile.
    - Tiles render through the `Pages/Shared/_LinkTile` partial. Its `LinkTile` view model comes from `LinkTileFactory` (`Pages/`), which applies the settings' local domains; `IndexModel` and the Editor handlers both use it. A status bar panel renders through the `_StatusBar` partial, from a `StatusBarPanelModel`.
    - **Panels** are the full-width cards in two zones, above (`Top`) and below (`Bottom`) the category grid, rendered by `_PanelZone`. Today's are the search box (`_SearchPanel`, a GET form to `/Search`) and status bars, of which there may be several. The search box's ⌕ is a Bootstrap dropdown of the engines in Settings order (`search-panel.js`): choosing one enables the form's hidden `engine` field for the next search only, resetting after a submit or a back/forward-cache restore. The search card doesn't clip its overflow, and lifts itself while the menu is open, since each translucent card is its own stacking context. Keep additions visually compatible with the card/grid layout. Outside edit mode a panel with nothing to show is left out, and an empty zone renders nothing. In edit mode both zones render as drop targets, and each panel gets a handle and its kind's name, with an empty panel's reason in its place. Panels move within and between zones by drag or arrow keys through `OnPostReorderPanelsAsync` (zone by name, full ordered ID list; the other zone's gap is closed), and panel links don't navigate in edit mode. Edit-mode panels render as `_EditablePanelSlot`, whose ✎ opens `_PanelDialog` (`panel-dialog.js`); **+ Add panel** in the banner opens it for a new one.
    - The panel dialog (`modal-lg`) builds its fields from the kind's schema with the shared `option-fields.js` (`OnGetPanelKindsAsync` for Add, with each kind's availability, widget placement and widget limit; `OnGetPanelAsync` for an existing panel, with its values and widgets). A kind that holds widgets gets the shared widgets section (`_WidgetEditor`, `widget-editor.js` configured for the placement, with a Label field off tiles). It posts option values as `options[key]` (booleans as `true`/`false`), and the widgets as a JSON `widgets` field, to `OnPostCreatePanelAsync` / `OnPostUpdatePanelAsync`, which check the options with `OptionForm` and the widgets with `WidgetForm` for the kind's placement, and store compact JSON. Its live preview is `OnGetPanelPreviewAsync` (kind, options, widgets): the kind's own content with draft widgets, or a sentence for an empty panel or invalid options; `widget-preview.js` reads its pending widgets as in the link dialog. After a save the page swaps in `OnGetPanelSlotAsync`'s slot. Delete closes the zone's gap and returns a `PanelSnapshot`, widgets included; Undo posts it to `OnPostRestorePanelAsync`. Create and restore refuse a second panel of a single-instance kind, and a panel of an unknown kind can only be deleted.
    - The panel handlers live in `Pages/Admin/Editor.Panels.cs`, a partial of `EditorModel`.
    - **Quick launch** (`_QuickLaunch`, rendered in the `Dialogs` section outside edit mode, and `wwwroot/js/modules/quick-launch.js`): typing a character anywhere that isn't a field (or `/`) opens a fixed, non-modal box. It matches tiles client-side on label, description and host (every word must match; label prefix, then label word prefix, then label substring, then the rest; ties keep page order). It hides non-matching tiles, empty categories, the panel zones and the grid break with `quick-launch-hidden`, and pads `.app-content` (`is-quick-launching`) so the box doesn't cover the first matches. Enter opens the highlighted match (Ctrl/⌘ for a new tab), and Shift+Enter searches the web. With no matches, or a known `!shortcut` at the start or end, it lists `IndexModel.QuickLaunchEngines` (Settings order) and searches through `/Search`, adding `engine=` only for a non-default pick. It never opens while a modal or dropdown is open, and closes on Esc, an outside click, or a back/forward-cache restore.
  - `Pages/Shared/_Layout.cshtml` holds the navbar: theme toggle, Settings, then Edit/Done at the far right. Done shows in edit mode and in the list view (`ViewData["IsEditMode"]` / `ViewData["IsListView"]`) and returns to the dashboard. The list view is reached from the edit-mode banner, not the navbar. It injects `DashboardSettingsService` directly for the title, motto and theme. It also holds the inline pre-CSS theme script and the background renderer, which draws through `wwwroot/js/lowpoly.js`, a small dependency-free replacement for Trianglify (Trianglify is GPL-3.0). The layout renders the page's one antiforgery token for `api.js`, and the `#toast-host` container used by `wwwroot/js/modules/toast.js`.
    - Modal dialogs go in the layout's `Dialogs` section, never inside the page body. `.app-content` has a `z-index`, so a modal inside it is trapped under Bootstrap's backdrop and can't be clicked.
  - `Pages/Admin/*` (Editor, Settings) require the `Admin` policy (`AuthorizeFolder` in `Program.cs`). Its only requirement, `AdminRequirement`, is satisfied for everyone by `AllowAllAdminHandler` (`h2s/Authorization/`). That's the authorization seam: authentication will come from a homelab-wide project, which replaces the handler. Don't add login or authentication to h2s itself.
- **Panels** (`h2s/Panels/`, namespace `h2s.Panels`): each `Panel` row (`Kind`, `Zone`, `SortOrder` within its zone, `OptionsJson`) is rendered by its **kind**, an `IPanelKind`. The interface is shaped for Phase 5's widget abstractions: if it can't express the built-in panels, it's wrong.
  - A kind declares a `Key` (stored, never changed), `DisplayName`, `IsSingleInstance`, an option schema of `SchemaOption`s, the same schema connections use (see Integrations below), and a `WidgetPlacement` (default `None`): a kind that holds widgets, as a status bar does its items, names the placement they must allow. The core loads a panel's widgets (`WidgetService.GetForPanelAsync`, cached results only) and passes them in `PanelContext.Widgets`.
  - `GetContentAsync (PanelContext)` returns `PanelContent.Show (partial, model)` or `PanelContent.Empty (reason)`. Kinds are singletons and resolve request services from `PanelContext.Services`.
  - Kinds are registered as `IPanelKind` singletons in `Program.cs`; `PanelCatalog` lists them and `PanelService` (scoped) loads the panels and builds their content. A panel whose kind is unknown or throws comes back empty (and is logged) rather than breaking the page.
  - Built-in kinds: `search` (`SearchPanelKind`, single-instance: placeholder text, blank for "Search with" and the default engine's name; empty when there are no engines) and `status-bar` (`StatusBarPanelKind`, any number: an optional title shown at its start and an optional link URL the bar opens, such as a status page; its items are status-bar widgets from any integration, at most 20, each shown under its label; empty with no items).
  - `DefaultPanels.Create ()` is the starting set: status bar, then search, in the top zone. The AddPanels migration inserts the same, with literal kind keys.
- **Integrations and connections** (`h2s/Integrations/`, namespace `h2s.Integrations`; the contracts are in `h2s.Widgets.Abstractions`). The core disposes, integrations propose: an integration declares what its connections need, and the core renders, stores, checks and secures it.
  - **Option schemas** (`h2s.Widgets.Abstractions`) serve panels and connections alike. A `SchemaOption` is text, URL (absolute http(s), no credentials), integer, boolean, secret or select (one of its `Choices`, each an `OptionChoice` of value and label; an optional select may be blank, which the form labels with the `Placeholder`), with label, help text, placeholder, default, required flag, integer bounds and a text `Pattern` (full match, with a `PatternDescription` for the error). The form also uses `Pattern` as an HTML `pattern`, so it must be valid in a JavaScript `v`-flag regex too: escape a hyphen in a character class. A widget kind's text or integer option may name a **choice list** in `ChoicesFrom`, one its integration publishes through `IIntegration.GetChoicesAsync (listKey, ConnectionContext)` (a `ChoiceList` of `OptionChoice`s with an optional `Group`, `ChoiceList.Unavailable (reason)` when the service can't be read, `null` for no such list). The option keeps its type and checks; the form offers the list beside its usual field (see the link dialog below). `OptionValues` reads stored JSON against a schema: unknown keys are ignored, and missing, mistyped, out-of-range, unmatched or (when required) blank values take the default. Secrets come separately, already decrypted, and never appear in `Values`. `OptionForm` (`h2s/Options/`) checks posted values against a schema and produces the stored JSON (text at most 200 characters; it skips secrets), and `TryResolveSecrets` works out the secrets to store: a typed one replaces, a blank one keeps what's stored unless `clearSecrets` names it, and a required one must end up set. `OptionDescriptions.Describe` turns a schema into the JSON `wwwroot/js/modules/option-fields.js` builds fields from (no secret values, ever); the panel dialog and the integration cards both use it.
  - `IIntegration` declares a `Key` (stored, never changed), `DisplayName`, `Description` (its card's intro), `AllowsMultipleConnections`, its `ConnectionOptions` schema, and optional hooks with default implementations: `Validate (OptionValues)` for rules beyond the schema (synchronous, no network; save and import both call it), `TestAsync (ConnectionContext)` for Settings' Test button, and `GetChoicesAsync` for its choice lists. `ChoiceListReader` (`h2s/Integrations/`, scoped) reads a list through the integration's first connection, turning a missing connection or an exception (logged) into a list with a reason. Integrations are `IIntegration` singletons registered in `Program.cs`, listed by `IntegrationCatalog`.
  - A `Connection` row holds one integration's settings: `IntegrationKey`, `Name` (unique per integration), `OptionsJson`, and `SecretsJson`, encrypted by `ConnectionSecrets` with Data Protection (purpose `h2s.connections.secrets`). Secrets that can't be decrypted (lost keys) read as not set, never as an error, and they're never exported or sent to a browser.
  - `ConnectionService` (scoped) reads and saves connections. It caches them in `IMemoryCache` (5 minutes) and hands out copies; its writes and imports clear the cache, so in integration tests add connections (`TestConnections.AddUptimeKumaAsync`, `AddJsonApiAsync`) before the first request. `DashboardApplicationFactory.ConfigureServices` registers extra services, such as a test-only integration with a secret.
  - **Uptime Kuma** (`h2s/Integrations/UptimeKuma/`) is the first integration: single-connection, with `serverUrl` (required; `Validate` wants a base URL), `apiKey` (a required secret) and `defaultUptimeWindow` (a select of `UptimeKumaWindows`: `1d`, `30d`, `365d`; default `1d`). `UptimeKumaSettings.From (OptionValues)` gives a connection's typed settings; its `ApiKey` is left out of `ToString`. The status page slug it once had became the status bar's link (ConvertGroupsToStatusBarWidgets; `LegacyStatusPageSlugOption` for older backups). The MoveUptimeKumaToConnection migration moved the three former `DashboardSettings` columns into that connection, and UseUptimeWindows turned periods in hours into windows (the shortest that covers them: up to 24 hours is `1d`, up to 720 is `30d`), both with literal keys.
  - **JSON API** (`h2s/Integrations/JsonApi/`, key `json-api`) is the second: single-connection, for any service that answers JSON. Its connection has `baseUrl` (a URL, required; `Validate` allows a path prefix such as `/api` but no query, fragment or credentials, via `JsonApiUrls.IsValidBaseUrl`), `auth` (a select of `JsonApiAuth`: `none` (default), `basic`, `bearer`, `header`), `username` (basic), `headerName` (header, with an HTTP-token `Pattern`) and `credential` (an optional secret: the password, token or header value). `Validate` wants a username for basic and a header name for header, but not the credential, since import calls it without secrets and secrets are never exported; `JsonApiSettings.AuthProblem` reports a missing credential instead, from `TestAsync` and as the widget's Unknown result. `JsonApiSettings.From (OptionValues)` gives the typed settings; its `Credential` is left out of `ToString`. `TestAsync` GETs the base URL with the authentication (2xx success; 401/403 danger, "refused the credentials"; any other status a warning that names it, since widgets read paths under the base; network failures go to `UrlProbe`). It needs no migration or backup version: connections and widgets already round-trip generically.
    - `JsonApiClient` (`h2s/Services/`, scoped, named client `JsonApi`, 10 s timeout) sends GET with `Accept: application/json` and the authentication (`Authorization: Basic` or `Bearer`, or the custom header), reads at most 256 KB (larger is `IsTooLarge`, never an exception), validates certificates and does not follow redirects (`AllowAutoRedirect = false`, so credentials only go to the host the connection names). It caches successful bodies for 15 s, keyed by the full URL and a hash of the authentication and credential, so widgets on one endpoint share a request; the connection test bypasses the cache.
    - **`json-api/value`** (`JsonApiValueWidgetKind`, Status role, so tiles and status bars, 60 s) shows one value as a pill. Options: `path` (required, relative to `baseUrl`, such as `/json` or `status?full=1`), `valuePath` (required), `name`, `unit` and `expected`. `JsonApiUrls.TryResolve` joins `path` to the base (a path-prefixed base keeps its prefix) and refuses anything absolute (a scheme, `//`, backslashes, a fragment, spaces) or that leaves the base's scheme, host, port or path prefix (`..`, also percent-encoded); `FetchAsync` does this before any request, and the option's `Pattern` also blocks a scheme or `//` at form time (the widget-kind contract has no validation hook of its own, so the live preview is where anything else shows). `valuePath` is parsed by `JsonValuePath` (no library): dot keys, `[n]` indexes, `["odd key"]` or `['odd key']` for awkward keys, empty or `$` for the whole document, with a clear error for bad syntax. Results: a string shows as-is (cut to 40 characters with `…`), a number as its JSON text, a boolean as `true`/`false`, an array as its item count (with the unit, or `item`/`items` when there is none); the pill is `WidgetStat.Text`, so the unit follows the value and `%` attaches. An object or null is a Warning; a missing path or index a Warning; a non-2xx status, a non-JSON answer or one over 256 KB an Error; an unreachable service, an invalid value path, a refused `path` or a missing credential Unknown. `expected`, when set, makes the status Ok if the value's text equals it (ordinal, trimmed) and Error otherwise. Descriptions are full sentences ("Slides is 2 slides.", "Status is degraded, not healthy.").
    - Tests: `TestConnections.AddJsonApiAsync` adds a connection to an integration test's app, and `TestConnections.ServeJsonApi` answers like one (`HttpbinJson` at `/json`, a bearer-protected root); the unit tests drive the widget kind through a stubbed `JsonApiClient`.
  - h2s reads Kuma through its **`/metrics`** endpoint (Prometheus text, read by `PrometheusText` into `KumaMetrics`), authenticated with the API key as the password of HTTP basic auth. One request reports every monitor, group monitors included: `monitor_status` (`KumaMonitorStatus`), `monitor_response_time`, `monitor_uptime_ratio` per window, and `monitor_cert_days_remaining` / `monitor_cert_is_valid`. `UptimeKumaClient.GetMetricsAsync` caches successful reads for 30 seconds, keyed by server and a hash of the key, so everything showing Kuma's data shares one request.
- **Widgets** (`h2s/Widgets/`, namespace `h2s.Widgets`; contracts in `h2s.Widgets.Abstractions`): live figures on links' tiles. An integration offers widget kinds through `IIntegration.WidgetKinds` (default none).
  - An `IWidgetKind` declares a `Key` (stored, never changed), `DisplayName`, a `Role`, an option schema and a `DefaultRefresh`, and `FetchAsync (WidgetContext)` returns a `WidgetResult`: a `WidgetStatus` (Unknown, Ok, Warning, Error, Inactive), a few `WidgetStat`s (label, value, unit, optional severity; `%` attaches without a space) and a `Description` sentence, the tooltip and what screen readers hear. Kinds never write HTML.
  - **Roles:** an `App` widget belongs to links of one app; a link has at most one, on the left of its tile's widget row. `Status` widgets suit any link, any number in order, as compact pills right-aligned in one group (`.link-widgets-status`), which wraps to the next line whole rather than splitting. Phase 6 may let app widgets stretch the tile.
  - **Placements:** a kind's `Placements` (flags of `WidgetPlacements`: `Tile`, `StatusBar`) say where its widgets may go, defaulting from the role (status: both; app: tiles only). The kinds handler offers, and `WidgetForm` and import accept, only kinds allowed in the place (`placement=tile|statusBar` on `WidgetKinds`, `WidgetPreview`).
  - A `Widget` row (`LinkId` or `PanelId`, exactly one, enforced by `CK_Widgets_OneOwner`; `ConnectionId`, `Kind` within the connection's integration, `OptionsJson`, `RefreshSeconds` or null for the kind's default, at least 15, an optional `Label` that status bars show and tiles don't, `SortOrder`) cascades from its owner and its connection, so **removing a connection deletes its widgets**; Settings' Remove confirmation counts them (`widgetCount` on the card). The owner is optional in the model, so taking a widget out of its owner's list doesn't delete it: `WidgetForm.Apply` returns the ones taken out for the caller to remove. AddPanelWidgets is the schema change and ConvertGroupsToStatusBarWidgets the data move, separate migrations because SQLite rebuilds a changed table only at the end of its migration.
  - `WidgetCatalog` (singleton) lists the kinds as `WidgetKindEntry`s, referenced as `integration/kind` (such as `uptime-kuma/monitor`). `WidgetFetcher` (singleton) keeps each result in `IMemoryCache` for the widget's interval, under a key that hashes the widget's settings (kind, options, interval) and its connection's, but not its ID, so changes show at once and widgets of the same settings, saved or not, share one result, shares one read among concurrent requests, and turns exceptions and its 10-second timeout into Unknown results (logged). `WidgetService` (scoped) loads links' and panels' widgets with cached results only (`GetForLinksAsync`, `GetForPanelAsync`, so a page never waits on a service) and reads one through the fetcher (`ReadAsync`).
  - The dashboard renders `_LinkWidgets` / `_Widget` inside each tile (`LinkTile.Widgets`); a widget without a result is a `widget-pending` placeholder. `GET /widgets/{id}` (`Pages/Widget`, `no-store`) returns one widget's partial, and `widgets.js` reads pending ones at once and every widget on its `data-widget-refresh` interval, pausing while the tab is hidden.
  - The link dialog's **Widgets** section (the `_WidgetEditor` partial and `widget-editor.js`, shared with the panel dialog) lists, reorders, edits and removes the link's widgets, adding them from `OnGetWidgetKindsAsync` (kinds whose integration has a connection). An option with a choice list gets a dropdown of it, read through `OnGetChoicesAsync` (integration and list; 200 with a `message` when it can't be read, 404 for no such list) once per opening of the dialog, with "Another value…" showing the option's own field, which is what's posted; while the list loads, or when it can't be read, that field shows alone. The widget list names a listed value by its label.
  - The dialog's **preview** shows the link's widgets, saved or not, including the one being edited once its fields are valid (`WidgetEditor.previewValue`). `OnGetTilePreviewAsync` takes them as a `widgets` JSON field and renders them through `WidgetService.DescribeDraftsAsync` with cached results only; their placeholders carry `data-widget-preview="<position>"` rather than `data-widget-id`, so `widgets.js` leaves them alone, and `widget-preview.js` reads each through `OnGetWidgetPreviewAsync` (the same JSON, a position and the placement; `WidgetService.ReadDraftAsync`). The widget form shows the edited widget's description as it reads, which is its test: there's no separate Test button. They're posted with the link as a JSON `widgets` field that `WidgetForm` checks (kind known and allowed in the place, integration set up, options through `OptionForm`, refresh 15 to 86400 seconds, labels up to 100 characters, one app widget, at most ten on a tile and twenty on a status bar) and applies; a form without the field leaves the widgets alone, and an unknown kind's widget is posted back with `keep`. Widgets use their integration's first connection. Link snapshots (`WidgetSnapshot`) carry them, so Undo restores them while their connection exists. The handlers are in `Pages/Admin/Editor.Widgets.cs`.
  - **Uptime Kuma's monitor widget** (`KumaMonitorWidgetKind`, `uptime-kuma/monitor`, Status role, 60 s): the monitor's status as the pill's colour, with its response time and uptime for a window (default the connection's), read from `/metrics`. Its monitor is picked from the integration's `monitors` choice list (`UptimeKumaIntegration.MonitorsList`: group monitors under "Groups", then the rest, each by name with its ID). Uptime shows two decimals from 99%, truncated so nearly 100% never reads as 100.
- **Search engines** (`SearchEngine`: `Name`, `UrlTemplate` with `{query}`, `Shortcut`, `IsDefault`, `SortOrder`) are core configuration, not panel options, so quick launch can use them without a search panel. The AddSearchEngines migration seeds Bing (default, `b`), DuckDuckGo (`d`) and Google (`g`), as `DefaultSearchEngines.Create ()` does. `SearchEngineRules` (`h2s/Validation/`) checks names, URL templates and shortcuts, for the Settings handlers and import.
  - `/Search?q=&engine=` (`Pages/Search`) redirects a query to its engine through `WebSearch.BuildUrl`: a `!shortcut` word at the start or end picks the engine; failing that, the `engine` ID the search box's menu chose; failing that, the default. An unknown shortcut stays in the terms, and an unknown engine ID is ignored.
  - The Settings order is the engines' priority: the search box's menu and quick launch's no-match list both follow it. A blank query, or no engines, redirects to the dashboard.
- **Installable app**: `/manifest.webmanifest` (`Pages/Manifest`) is built per request from the settings (name "h2s - <Title>", short name the Title, the motto as description) and served as `application/manifest+json`. Its icons are in `wwwroot/icons/` (192 and 512 px, a maskable 512 px on the dashboard's indigo, and a 180 px Apple touch icon), drawn from the favicon's molecule. There's deliberately no service worker. The layout links the manifest and icons, and its `theme-color` meta tags follow this browser's effective color mode (both variants, by media query, in Auto); the toggle's script updates them as it changes the theme.
- **Hosting**:
  - `/healthz` is a health check (DbContext) for Kubernetes liveness and readiness probes.
  - `UseForwardedHeaders` runs first and trusts `X-Forwarded-For`/`-Proto` from any address, because the app is only reachable through Traefik.
- **Editor and Settings are JSON-handler pages, not scaffolded CRUD.** The server renders the initial state, then client scripts call named page handlers (`OnPostCreateCategoryAsync`, `OnPostUpdateLinkAsync`, `OnPostReorderPanelsAsync`, …). When you change editor or settings behavior, update the Razor markup, the PageModel handler and the JS contract together.
  - `/Admin/Editor` is the **list view**: `wwwroot/js/modules/link-list.js` renders a filterable, sortable table of links from the page's embedded JSON (`LinkRow`s, with each link's widget count for the Widgets column), and refreshes it from `OnGetLinksAsync` after every change. Rows open the shared link dialog; bulk move and delete go to `OnPostMoveLinksAsync` / `OnPostDeleteLinksAsync`. Bulk-delete Undo restores the returned snapshots one at a time, in the order given, through `OnPostRestoreLinkAsync`. The page also hosts every handler edit mode's dialogs call, so keep its URL. Categories are managed only in edit mode.
  - **Settings** is a page of section cards (General, Appearance, Search, Integrations, Backup). Each one posts to its own JSON handler, and nothing posts the whole page:
    - **Search** (`modules/search-engines.js`, `_SearchEngineDialog`) lists the search engines from JSON; they reorder with SortableJS or arrow keys and save as they change. Its handlers are in `Pages/Admin/Settings.SearchEngines.cs`, a partial of `SettingsModel`. One engine is always the default while there are any: the first one added becomes it, marking another moves it, the default can't be unmarked, and deleting it hands it to the first engine left. Shortcuts are stored lowercase without their `!`, and are unique.
    - **Integrations** (`Settings.Integrations.cs`, `modules/integrations.js`) is a heading over one card per registered integration, in registration order. The Razor page renders each card's frame (title, description, Save, Test connection, Remove and its inline confirmation), and `integrations.js` builds the fields from the embedded `integrations-data` JSON with `option-fields.js`. The handlers take the integration's key: `OnPostSaveConnectionAsync` and `OnPostTestConnectionAsync` (posting `options[key]`, `secrets[key]` and `clearSecrets`) and `OnPostRemoveConnectionAsync`; save and remove answer the card's new description, and the card re-renders from it. A secret field shows Set / Not set with Replace and Clear (Clear only when it's optional), never its value; Test uses the stored secret for one left blank. Remove asks for confirmation instead of offering Undo, since Undo would need the secrets in the browser. Settings carries nothing integration-specific beyond these cards. Each integration has one connection here; a generic list of connections, with a picker for widgets, is a sub-phase of its own before Home Assistant.
    - `settings.js` drives the General and Appearance cards: `OnPostSaveGeneralAsync` and `OnPostSaveAppearanceAsync`. Each validates its fields and returns ProblemDetails, and saves through `DashboardSettingsService`. After a save, the navbar title and motto update in place, and Appearance passes the new site default to `window.h2sColorMode.setSiteDefault`, which the layout exposes; a browser with its own mode keeps it.
    - **Test connection** checks the card's values without saving, through the integration's `TestAsync`. Uptime Kuma's probes reachability and certificate trust with `UrlProbe`, then reads `/metrics` with the API key and counts the monitors and groups; the handler answers a `level` and a `message`.
    - **Local domains** use `chip-input.js`; the posted value stays the comma-separated string the server already parses.
    - The page model no longer binds a form: `DashboardSettings`' validation attributes aren't used for binding any more, and the handlers do the checking.
  - **Settings → Backup** (`wwwroot/js/modules/backup.js`) exports through `OnGetExportAsync` and imports in two steps: `OnPostPreviewImportAsync` checks the uploaded file and summarizes it, and `OnPostImportAsync` replaces everything. `DashboardBackupService` (`h2s/Services/`) does the work: `ExportAsync`, `TryRead` (format, version and field checks, up to ten errors, one per line in the problem detail), `Summarize`, and `ImportAsync`, which runs in one transaction and saves settings through `DashboardSettingsService` so the cache is cleared. The file format (`DashboardBackup` and its `Backup*` records) is versioned (`h2s-dashboard`, version 9; version 2 added `panels`, each with its options as a JSON object, version 3 `searchEngines`, version 4 each link's `openInNewTab`, off in older files, version 5 `connections`, each with its integration, name and options, which moved Uptime Kuma's settings out of `settings`, and version 6 uptime windows: the Kuma connection's `defaultUptimeWindow` and the status bar's `uptimeWindow` replace periods in hours, which older files' hours are converted to, version 7 each link's `widgets`, each naming its kind as `integration/kind` and its connection by name, so import resolves it to one of the file's connections, and version 8 dropped links' `monitorId`: an older file's monitor IDs read as Uptime Kuma monitor widgets, as the ConvertLinkMonitorsToWidgets migration converts them (`UseMonitorWidgets`), and version 9 gave panels their `widgets` (each with an optional `label`) and dropped `infrastructureGroups`: an older file's groups read as monitor widgets on its first status bar, and its Kuma status page slug as that bar's link (`UseStatusBarWidgets`). Bump the version and keep reading old files when it changes. Secrets are never exported; on import a connection keeps the secrets of the one it replaces (same integration and name). `TryRead` takes the `PanelCatalog` and the `IntegrationCatalog` to check panel kinds, integrations, single-instance limits and connection options (through `OptionForm` and `Validate`, a missing option taking its default). A file from before panels or search engines reads with no such list, and importing it gives the defaults (`DefaultPanels`, `DefaultSearchEngines`); a file from before connections turns its settings' Uptime Kuma values into a connection.
  - `h2sApi.postForm` posts a `FormData` (such as a file upload) as multipart; anything else form-encoded.
  - Client scripts call handlers through `wwwroot/js/api.js` (`h2sApi.getJson`, `h2sApi.postForm`), which sends the antiforgery token and turns error responses into `Error`s carrying the problem's `detail`.
  - There's no jQuery or jquery-validation: forms use native constraint validation (`required`, `pattern`, `type="url"`, Bootstrap's `was-validated`), and the server's ProblemDetails show inline. Don't bring them back.
  - New client code is no-build ES modules under `wwwroot/js/modules/`, loaded with `<script type="module">`; the layout's import map resolves relative imports to fingerprinted assets. Reorder handlers parse their ID lists with `OrderedIdParser` (`h2s/Validation/`).
  - JSON handlers report failures as RFC 9457 ProblemDetails (`application/problem+json`) via `this.BadRequestProblem (...)` / `this.NotFoundProblem (...)` (`h2s/Pages/PageModelProblemExtensions.cs`), not bare `BadRequest`/`NotFound`. Tests check them with `FormPoster.AssertProblemAsync`.
- **Color mode**: the `ColorMode` enum has the values `Auto` (0, follows `prefers-color-scheme`), `Light` (1) and `Dark` (2).
  - An inline script in the `<head>` of `_Layout.cshtml` sets `data-bs-theme` on `<html>` before CSS loads, so the wrong theme never flashes on load.
  - Per-browser preferences (this color mode, and collapsed categories) live in cookies that `ViewerPreferences` (`h2s/Services/`) reads, so the server renders them; nothing about them is stored server-side.
  - `DashboardSettings.ColorMode` is the site default. Each browser may pick its own with the navbar toggle, which keeps it in the `h2s-color-mode` cookie (`auto`, `light` or `dark`; `ViewerPreferences` in `h2s/Services/` reads it), so the layout renders the browser's mode, falling back to the site's, with no flash. The toggle works entirely client-side: it cycles the site default (no cookie), Light, Dark and Auto, then updates `data-bs-theme` and re-renders the background. Its titles come from `ViewerPreferences.DescribeToggle` on the server and a matching table in the layout's script.
- **Uptime Kuma integration**: enabled only when there's an Uptime Kuma connection (see Integrations above).
  - Kuma is read only through its monitor widget and choice list; h2s no longer loads Kuma's badge images anywhere.
  - Links have no monitor of their own any more: the ConvertLinkMonitorsToWidgets migration turned each link's `MonitorId` into an `uptime-kuma/monitor` widget (first among its widgets, with the kind's defaults; skipped when the link already had a monitor widget for that monitor or ten widgets, and dropped without a Kuma connection), and dropped the column.
  - The infrastructure groups are gone too: ConvertGroupsToStatusBarWidgets turned each into an `uptime-kuma/monitor` widget on the first status bar (labelled with the group's name, response time off, uptime as the bar showed it), made Kuma's status page that bar's link, and dropped the table.
- **Outbound HTTP** goes through named `IHttpClientFactory` clients registered in `Program.cs`, each with its timeout:
  - `JsonApiClient` (`h2s/Services/`) reads JSON APIs for the JSON API integration, with the connection's credentials, so its client never follows a redirect (see Integrations).
  - `UrlProbe` (`h2s/Services/`) checks that a URL is reachable, used by the Settings page for the Kuma URL. On a TLS auth failure it re-probes with the `UrlProbe.AcceptAnyCertificate` client, so it can report "untrusted certificate" rather than "unreachable". Never use that client to fetch content.
  - `IconCatalog` (`h2s/Services/`) suggests selfh.st icons by matching names against the CDN's `index.json`, and `SearchAsync` ranks icons for the dialog's icon picker (`icon-picker.js`, via `OnGetSearchIconsAsync`). It downloads the index once and caches it in `IMemoryCache` for 12 hours, retrying after a minute if the download failed. Keep that caching if you extend icon suggestion.
  - `PageMetadataReader` (`h2s/Services/`) reads what the link dialog suggests. People enter base URLs, so it follows HTTP redirects (at most five) and then up to two client-side redirects: a meta refresh, or a stub page's script `location` set to a string literal. It follows those from error pages too, which Plex needs (a 401 page with a script redirect), but never uses an error page's title.
    - It also finds the site's icon: the largest declared `<link rel="icon">`, `apple-touch-icon` or manifest icon (mask icons and maskable-only icons skipped, scalable counting as 512px), else `/favicon.ico` if it serves something other than HTML. The dialog offers it as `IconUrl` only when there's no selfh.st icon.
    - On the final pages it collects a title, cleaned by `CleanTitle` (generic parts like "Login", "Dashboard", "…sign in" and colon taglines dropped), and app names from the web app manifest (`short_name`, `name`) and the `application-name`, `apple-mobile-web-app-title` and `og:site_name` meta tags.
    - The label is the title, or else the first app name. `OnGetSuggestLinkAsync` matches icons against the label, the app names, the title and its parts, the host, and finally first words.
    - It fetches only http(s) URLs, reads at most 256 KB per page (64 KB per manifest), and caches only useful results.
  - Server-side fetches of internal hosts keep full certificate validation. A homelab CA is trusted by mounting it and adding its directory to `SSL_CERT_DIR` (see the README), never by switching to the accept-any client.
  - `TestConnections.ServeKuma` answers like a Kuma server (`KumaMetricsText` at `/metrics` for `KumaApiKey`, 401 otherwise); `AddUptimeKumaAsync (apiKey: …)` stores a key encrypted with the app's own Data Protection keys.
  - Tests replace the network with `StubHttpClientFactory` and `StubHttpMessageHandler` (`tests/h2s.Tests/Infrastructure/`). `DashboardApplicationFactory` stubs the `IconCatalog`, `PageMetadata`, Uptime Kuma, JSON API and `UrlProbe` clients. By default it serves a small icon index (`IconIndexJson`) and 404 elsewhere; set `Outbound` before the first request to change that.
- **Icons**: not stored locally. A link shows its selfh.st icon (`IconName`) if it has one, else its own `IconUrl` (such as a favicon), else a dot; `Link.GetIconUrl()` applies that order. `Link.NormalizeIconName()` / `BuildIconUrl()` produce selfh.st CDN URLs. `wwwroot/js/site.js` swaps a tile icon that fails to load for the dot. The older Editor page doesn't post `iconUrl`, and `OnPostUpdateLinkAsync` keeps the stored value when the field is absent, as it does for `openInNewTab`.
- **Validation**: custom validation lives in `h2s/Validation/`: `HttpBaseUrlAttribute`, `OrderedIdParser` and `SearchEngineRules`.
  - `Program.cs` sets `SuppressImplicitRequiredAttributeForNonNullableReferenceTypes`, so form-bound models must mark required fields with an explicit `[Required]`.
  - Optional non-nullable strings need `[DisplayFormat(ConvertEmptyStringToNull = false)]`. Otherwise an empty field binds as `null`.

## Conventions

- Accessibility (kept by the Phase 4d2 pass; keep new UI in line):
  - The layout's first focusable element is a skip link to `#main-content` (`main`, `tabindex="-1"`). Each page has one `<h1>`; the dashboard's is visually hidden. Category `<section>`s are named by their heading (`aria-labelledby="category-title-{id}"`); panels are plain `<div>`s, not unnamed regions.
  - Keyboard focus must be visible: tiles and the status bar link get a solid primary outline on `:focus-visible`. Don't rely on `--bs-border-color-rgb`, which Bootstrap doesn't define; use `color-mix(in srgb, var(--bs-border-color) N%, transparent)`.
  - Decorative images (tile icons beside their label) have `alt=""`; don't put `aria-label` on plain `<span>`s.
  - `site.js` returns focus to a dialog's opener when it closes (Bootstrap only does that for `data-bs-toggle` triggers), falling back to the same control in an item re-rendered with the same `data-link-id`/`data-panel-id`/`data-category-id`/`data-id`. Give new list items such an attribute.
  - `#toast-host` is a polite live region. Moves by keyboard are announced through each page's visually hidden live region.
  - `prefers-reduced-motion` turns transitions off in CSS, and SortableJS's `animation` is 0 then; new Sortable lists should do the same.

- Keep edits minimal and local.
- Stay within Razor Pages: no MVC controllers, no Blazor, no new frontend frameworks. Site styling goes in `h2s/wwwroot/css/site.css`.
- Client libraries are committed under `h2s/wwwroot/lib/`; don't load scripts from a CDN at runtime. h2s is MIT, so check a library's licence before vendoring it (no GPL).
- New services go in `h2s/Services/` and are registered as scoped in `Program.cs` unless they clearly need another lifetime. Keep the `AddHttpClient()`, `MapStaticAssets()` and `MapRazorPages().WithStaticAssets()` calls.
- Namespaces follow folders: `h2s.Authorization`, `h2s.Data`, `h2s.Integrations` (and `h2s.Integrations.UptimeKuma`), `h2s.Models`, `h2s.Options`, `h2s.Panels`, `h2s.Services`, `h2s.Validation`, `h2s.Pages`, `h2s.Pages.Admin`. The abstractions library is `h2s.Widgets.Abstractions`; it references nothing of the app.
- C# style: the root `.editorconfig` is the source of truth. Its ReSharper section is generated from the house ReSharper profile. `h2s.slnx.DotSettings` is the team-shared ReSharper layer. It holds the full house code-style settings, taken from the author's global ReSharper settings because the profile export alone was incomplete. It also holds what EditorConfig can't express: the member layout pattern and XML formatter settings. ReSharper may append `SettingsMigration` markers to it. Watch for migrations rewriting the layout pattern; one once swapped in a `#region`-based pattern, and the house pattern uses no regions. `Directory.Build.props` holds the shared project settings. In short:
  - 2-space indent, Allman braces, and a space before parentheses in calls and declarations (`Foo ()`). Aligned assignments, initializers and multiline arguments, and trailing commas in multiline lists. Lines wrap at 132 columns.
  - Qualify instance members with `this.` and static members with their type name (`Link.NormalizeIconName`).
  - Private fields are camelCase with **no** `_` prefix. Constants and static readonly fields are PascalCase.
  - `var` only when the type is evident.
  - File-scoped namespaces, with usings outside them. `JetBrains.Annotations` is a global using.
  - XML doc comments on public members (CS1591 is on, except in tests).
  - Named arguments for literal and other non-trivial arguments; single-argument calls stay positional.
  - Expression bodies are preferred for methods, operators and constructors. Braces are always required around the bodies of `if`/`else`, loops, `using`, `lock` and `fixed`, even single-line ones.
- Braces are always required so that Full Cleanup settles in one pass: with braces only for multi-line bodies, it would drop a statement's braces, wrap it, then restore them on the next pass. If a second pass ever changes anything, treat that as a settings problem to fix rather than something to repeat.
- Purely mechanical formatting commits go in `.git-blame-ignore-revs`. Locally, `git config blame.ignoreRevsFile .git-blame-ignore-revs`.
- Dark mode:
  - Prefer Bootstrap theme-aware utilities (`bg-body`, `bg-body-tertiary`, `text-body`, `text-muted`, `border`) and CSS variables (`var(--bs-body-bg)`, `var(--bs-border-color)`, `rgba(var(--bs-body-bg-rgb), …)`) over hard-coded colors.
  - Scope theme-specific overrides with `[data-bs-theme="dark"]` / `[data-bs-theme="light"]`.
  - JS visuals read `document.documentElement.getAttribute('data-bs-theme')` and re-render when it changes; the low-poly background is the reference implementation.
  - The background also follows the page's height, because pages like the list view build their content in script after it is first drawn. A `ResizeObserver` on `<body>` resizes it, measuring with the background collapsed so the page can shrink. `lowpoly.js` takes a per-page-load `seed` and hashes each grid position, so a redraw at a new size keeps the existing triangles; only the colour gradients stretch.
  - Translucent surfaces follow the existing `category-box`, `link-block` and `home-search-form` styles.

## CI and release

`.github/workflows/ci.yml` runs on pushes and PRs to `master`. It has three parallel jobs, all required by `master`'s branch protection:
- **Build and test:** a Release build with `ContinuousIntegrationBuild=true` (warnings are errors), then `dotnet test`.
- **Container image:** builds `h2s/Dockerfile` without pushing.
- **Code style and inspections:** `jb cleanupcode` must leave `git diff` empty. On failure, a `cleanup-patch` artifact holds the required changes. `jb inspectcode` then uploads an `inspectcode-sarif` artifact; it's informational and doesn't fail the build.

The style job is the slow one, at roughly 5–10 minutes.

`.github/workflows/publish-container.yml` publishes `ghcr.io/arkane-systems/h2s:<tag>` and `:latest` on tag push, but only if the tagged commit is on `master`. It first runs `ci.yml` as a reusable workflow and publishes only if that passes. Manual dispatch from `master` uses the latest tag; from any other branch it publishes a soak-test image as `:<branch>` and `:<branch>-<short sha>`, never touching the release tags.

Day-to-day work happens on feature branches off `master`, one PR into `master` per change, merged with merge commits (not squash, which would invalidate `.git-blame-ignore-revs`). A release is an annotated version tag (`0.4`, …) on `master`. The footer shows `<Version>` from `h2s/h2s.csproj` (through `AppVersion`), so bump it in a PR first: publishing fails when the tag doesn't match it.
